# راهنمای ادغام با سایر سامانه‌ها — نسخه ۰.۳.۰

این سند توضیح می‌دهد چگونه هر سامانه دیگر (پژوهشیار، برنامه‌ریز، پرتال دانشجو، اپ موبایل، LMS، ...) از خدمات «دستیار آموزشی و آیین‌نامه‌ای دانشجو۳۶۰» استفاده کند — از یک پرسش ساده تا حضور کامل چت‌بات هوشمند در صفحات آن سامانه.

> **هشدار:** تا زمانی که اسناد رسمی دانشگاه ثبت نشده، همه پاسخ‌ها بر اساس داده «نمونه و غیررسمی» است و با برچسب هشدار همراه می‌آید. هیچ پاسخی بدون استناد به سند ارائه نمی‌شود.

---

## ۱) سه الگوی استفاده

| الگو | مناسب برای | نحوه کار |
|---|---|---|
| **پرسش مستند (ask)** | وقتی در سامانه میزبان ابهام/سؤال/بحث آیین‌نامه‌ای پیش می‌آید | `POST /integration/v1/ask` با پرسش + پروفایل دانشجو ← پاسخ سه‌لایه با استناد |
| **خدمات منفرد** | جست‌وجوی آیین‌نامه، ارزیابی قاعده، مهلت‌ها، فرایندها، تیکت | هر کدام یک مسیر مستقل با اسکوپ جداگانه |
| **چت‌بات نصب‌شدنی (ویجت)** | حضور بصری دستیار در صفحات سامانه میزبان | یک تگ `<script>` در صفحه میزبان |

## ۲) احراز هویت: کلید API سامانه متصل

هر سامانه متصل یک **کلید** (قالب `d360_...`) + مجموعه‌ای **اسکوپ** دارد. کلید در هدر `X-API-Key` ارسال می‌شود:

```
X-API-Key: d360_0123abcd...
```

- مدیریت کلیدها: وب‌اپ ← «سامانه‌های متصل» (فقط مدیر سیستم) — ایجاد، چرخش، فعال/غیرفعال، لاگ فراخوانی‌ها
- کلید فقط هنگام ایجاد/چرخش کامل نمایش داده می‌شود؛ در فهرست ماسک می‌شود (`d360_0eb348…18d7`)
- درخواست بدون کلید ← `401` · خارج از اسکوپ ← `403` · عبور از سقف نرخ ← `429`
- هر فراخوانی (حتی ناموفق) در `integration_logs` با کد وضعیت، مدت و IP ثبت می‌شود

### اسکوپ‌ها

| اسکوپ | سرویس |
|---|---|
| `ask` | پرسش مستند سه‌لایه |
| `regulations.read` | جست‌وجو + دریافت آیین‌نامه‌های منتشرشده |
| `rules.evaluate` | ارزیابی قواعد قطعی چهارحالته |
| `deadlines.read` | مهلت‌ها و رویدادهای تقویم |
| `processes.read` | راهنمای گام‌به‌گام فرایندها |
| `tickets.create` | ثبت درخواست کارشناس برای دانشجو |

**اصل حداقل دسترسی:** به هر سامانه فقط اسکوپ‌های لازم را بدهید. مثلاً پژوهشیار نیازی به `tickets.create` ندارد و ویجت پرتال فقط `ask` می‌خواهد.

## ۳) پروفایل دانشجو (شخصی‌سازی پاسخ)

سامانه میزبان هرجا دانشجو را می‌شناسد، پروفایل را در فیلد `student` می‌فرستد — دو حالت:

```jsonc
// حالت الف) شناسه داخلی (اگر دانشجو در این سامانه حساب دارد)
{ "student_id": 1 }

// حالت ب) داده صریح از پایگاه سامانه میزبان
{
  "full_name": "علی محمدی",
  "level": "کارشناسی",
  "major": "مهندسی کامپیوتر",
  "entry_year": 1402,
  "gpa": 14.5,
  "passed_credits": 64,
  "flags": { "on_probation": false, "transcript_verified": false }
}
```

اگر `student` نفرستید، پاسخ عمومی است و لایه «وضعیت شخصی» حذف می‌شود. اگر اطلاعات ناقص باشد (مثلاً `entry_year` نیامده)، موتور به‌جای حدس، وضعیت «اطلاعات ناکافی» برمی‌گرداند.

## ۴) مرجع مسیرها (`/api/v1/integration/v1`)

### ۴.۱ پرسش مستند — `POST /ask` (اسکوپ `ask`)

```bash
curl -X POST http://127.0.0.1:8600/api/v1/integration/v1/ask \
  -H "X-API-Key: d360_..." -H "Content-Type: application/json" \
  -d '{
    "question": "دانشجویی با معدل ۱۴/۵ می‌خواهد کارورزی ثبت‌نام کند، شرایط چیست؟",
    "topic": "کارورزی",
    "student": { "level": "کارشناسی", "major": "مهندسی کامپیوتر", "entry_year": 1402, "gpa": 14.5 }
  }'
```

پاسخ: `answer` شامل `short` (پاسخ کوتاه) + `conditions` + `status_rows` (ارزیابی قطعی قواعد) + `next_steps` + `sources` (استنادها: عنوان سند، نسخه، ماده، صفحه، متن عینی، وضعیت) + `warnings` (برچسب نمونه/غیررسمی، پرچم OCR و تزریق) + `confirmations` (مغایرت‌ها و موارد نیازمند کارشناس). فیلد اختیاری `include_retired` فقط برای بررسی مقررات قدیمی (خروجی همیشه با برچسب «ملغی» می‌آید).

**تضمین‌ها:** سند ملغی هرگز قانون جاری ارائه نمی‌شود؛ پرسش بی‌ربط صادقانه `no_result=true` می‌گیرد؛ متن سند فقط «داده» است و دستور داخل آن اجرا نمی‌شود.

### ۴.۲ جست‌وجوی آیین‌نامه — `POST /regulations/search` (اسکوپ `regulations.read`)

```jsonc
// بدنه
{ "query": "سقف واحد دانشجوی مشروط", "student": { ... }, "limit": 5 }
// پاسخ: results[] = استنادهای هم‌سان (فقط اسناد منتشرشده)
```

### ۴.۳ دریافت سند — `GET /regulations/{document_id}`

فقط اسناد `published`؛ خروجی: متادیتا + همه مواد (`chunks`). سند غیرمنتشره ← `404`.

### ۴.۴ ارزیابی قاعده — `POST /rules/evaluate` (اسکوپ `rules.evaluate`)

```jsonc
// یا rule_id مشخص، یا query برای انتخاب قواعد مرتبط
{ "query": "معدل کارورزی", "student": { "gpa": 11.0 } }
// پاسخ: results[] = { title, status: satisfied|not_satisfied|insufficient_info|needs_review, missing, ... }
```

### ۴.۵ مهلت‌ها — `GET /deadlines?days=45&student_id=1` (اسکوپ `deadlines.read`)

مهلت‌های فعال پیشِ رو با تاریخ جلالی (`date_fa`) و `days_left`.

### ۴.۶ فرایندها — `GET /processes?query=کارورزی` (اسکوپ `processes.read`)

راهنمای گام‌به‌گام + مدارک لازم + سیستم مقصد (یادآوری: «ثبت موفق» هرگز از سمت دستیار اعلام نمی‌شود).

### ۴.۷ تیکت — `POST /tickets` (اسکوپ `tickets.create`)

```jsonc
{ "subject": "ابهام در مهلت حذف و اضافه", "body": "...", "student": { "full_name": "علی محمدی" } }
// تیکت با پیشوند نام سامانه میزبان ثبت می‌شود: [سامانه برنامه‌ریز (نمونه)] ...
```

### ۴.۸ خودآزمایی — `GET /whoami`

کلید، اسکوپ‌ها، سقف نرخ و شمار فراخوانی‌ها — برای health-check سامانه میزبان.

## ۵) چت‌بات نصب‌شدنی (widget.js)

در انتهای `<body>` صفحات سامانه میزبان:

```html
<script src="http://SERVER:8600/api/v1/integration/widget.js"
        data-key="d360_..."
        data-url="http://SERVER:8600"
        data-title="دستیار آیین‌نامه‌ای"
        data-position="left"></script>
```

- دکمه شناور گرادیانی + پنل شیشه‌ای راست‌به‌چپ با همان هویت بصری سامانه
- پاسخ سه‌لایه داخل خود ویجت: هشدارها، پاسخ کوتاه، شرایط، «وضعیت شما» رنگی، اقدام بعدی، کارت استنادها
- پروفایل پویا: سامانه میزبان قبل از ارسال، `window.DastyarStudent = { gpa: 14.5, ... }` تنظیم کند
- یا پروفایل ثابت با `data-student='{"gpa":14.5}'`
- کلید ویجت در صفحه میزبان دیده می‌شود → اسکوپ را فقط `ask` بگذارید و سقف نرخ جداگانه تعیین کنید (فیلتر Referer در نقشه راه است)
- صفحه آزمایش آماده: `http://SERVER:8600/integration-demo?key=d360_...` (شبیه‌سازی میزبانی در «پژوهشیار»)

## ۶) نمونه‌های سریع

### پایتون (پژوهشیار — بررسی خودکار پیش از ثبت طرح)

```python
import requests

BASE = "http://127.0.0.1:8600"
KEY = "d360_..."

def check_regulation(question: str, student: dict) -> dict:
    r = requests.post(f"{BASE}/api/v1/integration/v1/ask",
                      headers={"X-API-Key": KEY},
                      json={"question": question, "student": student,
                            "topic": "پژوهش"}, timeout=15)
    r.raise_for_status()
    ans = r.json()["answer"]
    return {
        "found": not ans["no_result"],
        "short": ans["short"],
        "sources": [(s["doc_title"], s["clause_ref"]) for s in ans["sources"]],
        "warnings": ans["warnings"],
    }

print(check_regulation("شرایط استفاده از دستیار آموزشی در طرح پژوهشی چیست؟",
                       {"level": "کارشناسی ارشد", "major": "مهندسی کامپیوتر", "gpa": 17.0}))
```

### جاوااسکریپت (برنامه‌ریز — نمایش مهلت‌ها در کارتابل دانشجو)

```js
const res = await fetch('http://SERVER:8600/api/v1/integration/v1/deadlines?days=30', {
  headers: { 'X-API-Key': KEY },
})
const { deadlines } = await res.json()
// deadlines[i] = { title, date_fa, days_left, notes }
```

## ۷) نکات امنیتی و عملیاتی

1. **کلید = رمز** — فقط روی HTTPS منتقل شود؛ در لاگ سامانه میزبان هم چاپ نشود.
2. **چرخش دوره‌ای** — از دکمه «چرخش کلید» استفاده کنید؛ کلید قبلی بلافاصله باطل می‌شود.
3. در نسخه نمونه، کلید کامل برای نمایش در رابط مدیریت ذخیره می‌شود؛ در استقرار عملیاتی توصیه می‌شود فقط `api_key_hash` نگه‌داری شود (ستون موجود است) و نمایش کلید حذف شود.
4. **سقف نرخ** برای هر سامانه جداگانه است؛ برای سامانه‌های پرترافیک عدد بالاتر و برای ویجت‌ها عدد پایین‌تر بگذارید.
5. همه فراخوانی‌ها لاگ می‌شوند؛ از صفحه «لاگ» هر کارت، وضعیت مصرف را ببینید.
6. پاسخ‌ها همیشه فیلد `meta.sample_data=true` و برچسب «نمونه و غیررسمی» دارند تا در UI سامانه میزبان هم قابل نمایش باشد.

## ۸) نقشه راه ادغام (فاز بعد)

- فیلتر دامنه (Referer/Origin) برای کلیدهای ویجت
- وب‌هوک رویدادها (مثلاً «سند جدید منتشر شد» به سامانه‌های مشترکpush شود)
- احراز mTLS برای سرویس‌های حساس
- هم‌نشینی با زیرساخت مشترک دانشجو۳۶۰ (پروفایل واحد، SSO سراسری)
